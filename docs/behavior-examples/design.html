1. 方案摘要

用户发起的一次导出工作称为导出任务，该工作的每轮执行称为执行尝试。失败任务重试时保留任务 ID，增加一次有独立新 ID 的尝试；同一个任务可以有多次尝试。定义沿用 报表领域词典 r1，本稿只补技术映射，不另建词典。

现有 backend/export.py 已有失败检查、追加尝试、任务回到排队的局部逻辑。建议复用该逻辑：ExportJob 对应导出任务，attempts 中一项字典对应执行尝试。业务名称统一不要求修改历史类名或接口路径。

完成边界工程只有内存对象与同步函数，未提供路由注册、调用方、执行器、持久化或页面源码。局部设计已形成；不能由此证明新 ID、完整状态、真实接口与并发保证，整体保持草稿。普通非失败任务被函数拒绝；受理只代表排队，响应丢失不能据此认定未生效。本轮只交付设计。

2.2 正确性约束

约束及来源范围／窗口保证机制与缺口异常、并发与验证
INV-1：保留任务 ID；REQ-1同一失败对象，一次普通同步调用前后。retry 不改 job.id，返回原对象。静态已核对；后续真实函数测试 ID 与对象身份，不能证明跨进程归属。
INV-2：新增尝试及新 ID；REQ-1每次合法重试，保留已有历史。append 新增一项且不改旧项；新 ID 来自调用方，唯一性未受函数保证。重复 ID 仍可被追加，Q-1 阻塞完整保证；验证历史不变及重复输入的实际行为。
INV-3：仅失败任务可重试；已有函数契约入口 status 为 failed；普通串行调用。非 failed 在 append 前抛 ValueError；接受后任务、新项均 queued。拒绝时无该函数业务写入；校验与写入非一个原子整体，图 F-3 说明竞争缺口。
INV-4：任务、尝试分别区分四态；REQ-2两类对象各自的排队、执行、成功、失败语义。各有 status；不新定任务永远等于最新尝试的聚合规则。仅明确 queued 和任务 failed；Q-2 待查完整编码与转换，不从 str 推出四态校验。
INV-5：路径及标题兼容；AC-1历史接口与页面使用方。设计不改旧路径或“我的导出”。实际路由、页面缺失，Q-3 待查；后续运行验证，不把路径搜索当 HTTP 通过。

3. 现状及目标架构

ExportJob 是 dataclass，默认 status=queued、attempts 为独立空列表。retry 同步修改并返回传入对象，未见调用者。目标是沿用结构与真实重试机制，不新增组件。ID 生成、持久化、实际执行与用户归属不能从此对象推出。历史 HTTP 路径仅有注释，前端仅有需求标题约束，均须区分目标与已实现现状。

4. 核心流程与状态

业务状态（REQ-2）任务实际编码尝试实际编码本次安排
排队默认及重试后 queued新项 queued保留各自状态；受理不是成功。
执行未给未给保留业务语义，Q-2 查既有编码与转移，不新定英文值。
成功未给未给同上；返回 job 不是导出成功。
失败failed 是重试条件未见设置失败任务可回排队，不覆盖历史尝试。
场景结果及副作用恢复／限制
非 failedValueError("only failed tasks can retry")，本函数未改对象。不编造 HTTP 400／409 等映射。
串行接受ID 不变，追加一项 queued，任务 queued，历史不变。新 ID 由调用方保证的证据缺失。
立即串行重复同一对象已 queued，第二次拒绝。这不是请求 ID 去重；以后再 failed 仍可追加。
重复尝试 ID任务 failed 时仍可追加相同 ID。Q-1 未解，不宣称已满足新 ID 保证。
并发／不同副本可能同时通过 failed 检查。无共同原子边界，不承诺只受理一次；F-3。
追加后中断／响应丢失无撤销逻辑，调用方可能不知已否接受。超时不等于未生效；不盲重试或删尝试，核实入口待 Q-3。
取消、文件或外部执行失败本函数无取消入口、文件、连接或调度动作。不推断执行器清理与补偿，不扩建基础设施。
