## 阻塞发现

### R1 [P1] total 忽略数量，产生错误合计

- 位置：`orders.py:2`；来源：已提交变更。
- 触发：任一行 `qty` 不为 1。例如 `total([{"price": 10, "qty": 2}])`。
- 实际／预期：实际 10，按规格应为 20；两行价格与数量分别为 `(10, 2)`、`(3, 4)` 时实际 13，应为 32。
- 因果与影响：将起点的 `price * qty` 改成只加 `price`，数量不再参与业务计算，合计错误。
- 依据：`spec.md:1` 的“total按price*qty求和”；已直接执行最终工作区的 `total`。
- 最小修复方向：恢复逐行乘数量再求和；以独立业务期望值补充数量不为 1 的断言。

### R2 [P1] can_view 无条件允许非 owner

- 位置：`orders.py:4-5`；来源：暂存变更，最终工作区保留该行为。
- 触发：owner 和 actor 不同，例如 `can_view("alice", "bob")`。
- 实际／预期：实际 True，应为 False；owner 相同时仍为 True，不能用该成功场景证明权限有效。
- 因果与影响：原有 `owner == actor` 被替换为 `True`，该权限函数对所有调用者放行，违反订单查看边界。
- 依据：`spec.md:1` 的“只有owner能查看订单”；已直接执行允许与拒绝场景。仓库未提供 HTTP 路由或其它业务调用者，因此本报告证明该函数的越权放行，不虚构线上接口泄露已经发生。
- 最小修复方向：恢复 owner 与 actor 的授权比较，并增加非 owner 拒绝断言。

### R3 [P1] list_orders 返回其它 tenant 的订单

- 位置：`orders.py:7-8`；来源：未暂存变更。
- 触发：输入同时包含 tenant-a 与 tenant-b 的订单，调用 `list_orders(orders, "tenant-a")`；或查询没有订单的 tenant-c。
- 实际／预期：实际均返回两条完整输入；tenant-a 应只有自己的订单，tenant-c 应为空列表。
- 因果与影响：起点逐行比较 `row["tenant"] == tenant` 的过滤被直接返回输入替代，tenant 参数失效。函数返回结果包含其它租户的数据。
- 依据：`spec.md:1` 的“订单列表必须隔离tenant”；使用真实函数和混合租户数据复现。
- 最小修复方向：按请求 tenant 过滤，覆盖混合租户和无匹配租户场景。

### R4 [P1] 已接通的查找实现忽略 ID，总是取首条

- 位置：`lookup.py:1-2`；入口为 `orders.py:10-12`；来源分别为未跟踪新增实现、未暂存调用接线。
- 触发：订单列表非空，请求第二条订单的 ID 或不存在的 ID。例如列表为 A、B 两条时，`get_order(orders, "B")` 和 `get_order(orders, "missing")`。
- 实际／预期：实际都返回 A；前者应返回 B，后者应返回 None。
- 因果与影响：`get_order` 确实调用新增 `find_order`；后者完全不读取 `order_id`，只返回 `orders[0]`。因此这不是未接入的遗留函数，用户指定的最终工作区确实包含该错误路径。
- 依据：`spec.md:1` 的“按ID查找返回匹配订单，未找到返回None”；分别直接调用入口和查找函数复现。示例使用 `id` 字段；当前实现忽略参数这一因果不依赖字段名称。
- 最小修复方向：按订单 ID 匹配并在无匹配时返回 None；覆盖第二条匹配、非空列表无匹配、空列表。
