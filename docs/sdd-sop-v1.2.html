01

先选你的任务

SDD 是“先把需求与关键设计说清，再按可验证任务实施”的开发方法。本手册帮助研发、测试和业务确认人使用当前这套通用 skill 协作，适用于新项目与已有系统。

提供目标、原始需求和项目位置，使用 sdd-workflow。按完整 SDD 推进，在需求和设计确认点作决定。

记住两个结束状态

研发完成后报告“研发完成，待独立验收”，交付提测材料并结束当前入口。测试岗位另行发起验收，给出有实际证据的结果，并由测试工程师负责岗位确认。

02

全流程与岗位分工

责任划分：共享依据，分别承担完成责任
岗位／角色承担的工作确认或完成责任
研发工程师需求事实调查、技术设计、开发用例、计划、应用代码、开发验证、修复与提测。对研发交付范围、可测试性及证据真实性负责。
测试工程师独立设计验收用例，在独立验收工程维护脚本和数据，组织 UI／真实集成／E2E 验收与复测。对验收范围、执行结论及测试岗位确认负责。
需求／设计确认人（用户）决定业务规则、范围和重要取舍，确认需求闭环与当前设计；重大偏差时重新对齐。确认必须对应实际内容和版本；已有有效决定直接复用。
AI 助手辅助当前岗位调查、撰写、实现、验证、审查及记录。事实、建议、未知分开；不能代签、虚构运行或把自查当独立审核。
环境协作方（按团队实际分工）协作提供可部署构建、测试环境、访问权限和必要运维支持。明确实际提供者与前提，不默认由某一岗位独自补齐。
需要人工决定的节点是明确的

完整 SDD 中的需求确认、设计确认，以及推翻已确认内容或出现重大风险／取舍时的再对齐。普通实施细节和已授权的可逆工作自主推进。代码审核与测试岗位结论按各自完成标准记录，不扩展为每一步都要人工批准。

03

开始前准备：够用即可，不必一次补齐所有信息

最小准备清单
准备项先提供／核对什么暂缺时怎么处理
任务与目标原始诉求或 Bug 现象、正确预期、明确不做项；可从一段话开始。AI 先整理已知与未知，查证事实；业务决定留给确认人。
工作工程与约束正确项目／分支／目录、现有工作区改动、适用项目规则、实际构建和测试配置。先读取必要范围；保留他人改动，不假设其他宿主的 hooks 已生效。
特性与产物定位现有任务标识、目标版本、主业务模块、受影响模块、既有特性包及登记位置。按用户指定、项目规范、已登记路径、默认层级的优先级解析一次，后续阶段沿用。
有效来源已有需求／设计／接口契约、确认记录、相关日志或复现证据、当前任务进展。说明来源和版本；文件存在不能证明已确认、接通或完成。
当前岗位与入口研发交付使用 sdd-workflow；测试准备／验收使用 sdd-acceptance。不清楚时根据任务先判断；涉及写验收脚本前，必须明确独立验收工程。
验证与环境已有测试框架、命令、可用 mock／隔离接缝、QA 可用环境与权限。命令从配置查证；环境缺口如实记录，继续可独立推进的工作。
交接方式双方可访问的需求、代码／构建和证据引用，版本如何对应。可以先准备交接索引或补丁；本地文件存在不代表另一岗位已收到。

第一次使用 skill

  1. 确认宿主能找到九个 sdd-* skill，以及需求澄清时引用的 grilling；只加载当前阶段和直接需要的引用。
  2. 告诉 AI 当前任务、工作工程、目标岗位、已有决定和限制。第 12 节提供可复制指令。
  3. 让 AI 返回本次流程路径、稳定特性标识、实际产物根目录、当前阶段、依据及下一步。分流明确后按顺序执行已确认范围。

当前支持在 Codex、Claude Code、Cursor 使用。这里的“调用 skill”指让宿主读取并应用相应 SKILL.md，不假设三端有统一的 slash-command API。技能发现方式与可用工具以实际宿主配置为准。

04

任务分流：让流程深度与风险匹配

五项全部满足，才进入简单 Bug 直接修复路径
简单 Bug 准入条件必须有的判断依据容易误判的情况
1. 预期明确正确行为有已确认规则、契约或可靠证据，无须新增产品决定。把“目前代码这样写”当作业务正确答案。
2. 根因明确复现、日志或代码因果证据能够解释问题与修复为何有效。看到表象就补 fallback，掩盖真正缺陷。
3. 影响有界检查必要入口、调用方和共享机制，能说明受影响与不受影响范围。只看改动文件，漏掉共享组件或其他模块。
4. 风险较低保持既有契约、数据含义和核心业务规则，修改容易撤回。只有一行的权限／数据变更也可能高风险。
5. 可以验证能以合理成本证明原问题修复，并覆盖最可能受影响的相邻行为。只有 lint 通过；或者目标行为已经被 mock 掉。

三条具体路径

  • 新增模块／功能扩展：完整 SDD，依次完成需求、设计、用例、计划、实施验证、审核和提测。
  • 简单 Bug：简短分流记录 → sdd-implement 修复与针对性开发验证 → 必要代码复核 → 按范围提测。不强制新建完整 PRD、设计和计划。
  • 复杂 Bug：先报告根因证据、影响、未知、可行选项和推荐，由人工决定从需求、设计、计划或实施切入。只重做受影响部分。

信息不足先自主有界诊断。需要 UI 或真实依赖才能完成的那部分证明，保留“待验收／未验证”；不能用后置安排掩盖开发阶段本应完成的隔离验证。修复中发现契约变化、重要安全／数据风险或影响扩散，立即重新分流。

分流输出可以很短，但要有理由

至少写清：任务类型与进入点、五项准入的结论与依据、开发验证办法、待测试岗位补足的证据，以及未决事项。

05

研发工程师：从任务到提测的操作步骤

完整路径按下列顺序推进。业务用例与技术设计可以在需求闭环后分别准备；进入实施仍以当前设计获得确认、实施条件具备为前提。

D1 · 需求验证与闭环

sdd-requirement-validation
输入
原始诉求、现有能力与业务事实、已知范围和约束。
操作
  1. 查证相关事实，按“合理、闭环、边界、交互与结果可验收”四维检查。
  2. 对规则和决策缺口分级：阻塞项必须解决；非阻塞澄清记录影响。
  3. 有必要时引用 grilling，按依赖顺序提问并提供选项与理由；已知决定不重复问。已知信息足够时直接验证。
  4. 将决定回写需求，再检查四维和验收条件，生成可评审 HTML。
产物
requirements.html；稳定 REQ／AC；四维结论、来源、开放问题、版本与确认状态。
完成／交接条件：四维成立、阻塞为零、每条可验收且 PRD 自检完成时，为“专业检查完成，待用户确认”。用户确认当前内容后，才是“需求已闭环”。

D2 · 技术设计与开发用例

sdd-design ＋ sdd-test-cases
输入
已确认需求／验收条件，相关源码、配置、契约和项目约束。
操作
  1. 说明现状、目标差异及真实可行的取舍；复杂知识、关系、流程优先用图解释。
  2. 提取关键正确性约束，说明作用范围、保证机制及失败／并发下的行为。
  3. 明确职责、字段、错误、权限、状态、资源、副作用、影响和恢复边界。
  4. 从已确认需求设计业务用例；接口等契约明确后补技术用例，不能猜接口或规则。
  5. 安排研发隔离验证和 QA 待验收项，写清两岗位代码工程和可测试前提。
产物
design.html、研发 test-cases.html，以及设计／需求／用例关联。
完成／交接条件：关键保证、契约、状态、失败处理和必要图解明确，阻塞已处理时为“设计就绪，待确认”。用户确认当前设计后进入实施准备。用例就绪另行判断，不代表已执行。

D3 · 拆分可验证的实施任务

sdd-plan
输入
有效需求与设计确认、相关用例、实际框架／命令与开发条件。
操作
  1. 按可交付的行为切任务，写清稳定任务 ID、需求来源、依赖、修改边界和预期结果。
  2. 纳入必要 fixture／替身、单元／接口／功能／契约验证、清理及适用静态检查。
  3. 查证测试命令，筛出符合当前阶段的子集；UI／真实集成／E2E 单列为 QA 交接项。
  4. 计划覆盖代码审核和提测材料；普通工作默认顺序推进，不自动派发或触发远端验收。
产物
项目现有任务格式，或 tasks.md。
完成／交接条件：研发范围被完整覆盖，每项能执行、能验证，阻塞依赖有处理办法。计划就绪仍不代表实现完成。

D4 · 编码、开发测试与作者自查

sdd-implement
输入
当前任务与用例、有效确认、项目规则；简单 Bug 则使用分流依据。
操作
  1. 实施必要改动，复用既有机制，保护已有工作；不顺带做无关重构。
  2. 在对应前后端项目 test/ 维护相关开发测试，保留真实被测逻辑，隔离昂贵外部依赖。
  3. 执行所需单元、接口、非 UI 功能、契约及适用静态检查；核对正常、异常、边界、相关并发／重复及副作用。
  4. 适合自动化的 Bug 尽量证明“修复前暴露问题，修复后通过”。解释关键路径、异常、资源释放和部分成功后的状态。
  5. 记录版本、命令、实际结果、真实／替身边界和缺口；发现重大偏差重新分流。
产物
实际代码与开发测试，任务映射和执行证据。
完成／交接条件：范围实现、本阶段必要验证通过及适用检查完成，标记“实现就绪”，交代码审核。所有 UI 执行仍后置。

D5 · 独立判断、代码审核与修复复核

sdd-review-code
输入
真实代码改动、有效需求／设计、必要调用关系、项目约束和开发验证证据。
操作
  1. 先对原始约束与真实改动形成判断，再参考作者解释，避免仅复述自查结论。
  2. 复用静态检查结果，检查需求接通、异常／资源、测试有效性、安全、可观测性和相关运行风险。
  3. 发现写明位置、触发条件、后果、依据、严重程度与最小修复方向；区分实证缺陷、证据缺口和维护建议。
  4. 修复阻塞并按影响定向复核，核对特性登记、实际路径、产物修订和证据关联。独立评审能力不足时如实说明；高风险工作加强适当独立复核或人工判断。
产物
代码审核结论、发现与处理记录、审核范围、独立性限制和剩余待验收项。
完成／交接条件：阻塞均已处理且相关修改复核完成，才可审核通过。后置 UI／真实 E2E 未执行保持待验收；开发期必要隔离测试缺失仍是证据缺口。

D6 · 提测交付，结束研发入口

sdd-workflow
输入
实现就绪、必要开发测试和静态检查完成、代码审核通过。
操作
  1. 按提测清单关联实际需求／设计、当前代码／构建及开发证据。
  2. 说明变更、排除项、入口、配置／数据变化、待 UI／真实依赖／E2E 验收场景及前提；按影响更新模块索引与现行知识，登记可核实的交付基线。
  3. 输出“研发完成，待独立验收”并结束本入口。分别记录研发状态和 QA 状态。
产物
提测索引（例如 handoff.md）及可对应版本的材料引用。
完成／交接条件：研发范围与证据完整，交接内容与实际版本一致。结束后不自动调用、触发或等待 sdd-acceptance／验收 CI。
06

开发测试与代码质量控制

开发期需要充分验证；成本影响环境选择和频率
开发验证层级保留的真实目标应有的判断
单元函数、规则或状态转换；按需替换时钟、随机和 I/O。返回、异常、边界和状态是否符合规则。
接口实际入口／路由、校验、相关鉴权、业务处理和序列化。契约与错误语义、允许／拒绝配对、拒绝无意外副作用。
非 UI 功能场景相关的真实业务组件与操作链路。业务结果、状态、事件、重复／失败及恢复；不能只验状态码。
契约真实消费方处理或真实提供方响应；各自外部边界可隔离。约定与实现一致。契约通过不能单独证明真实持久化或送达。
静态与规范现有 lint、格式、类型、构建和适用安全扫描。遵循项目规则、区分已有基线和新增问题，不臆造复杂度或覆盖率阈值。

代码审核如何落实质量要求

风险驱动审核，不靠作者自述自行批准
审核维度重点看什么可接受的依据
需求与真实接通入口、注册、调用、配置及共享机制；代码是否实际可达。当前改动与 REQ／AC／设计对应，必要调用路径可核实。
边界、异常与资源空值、边界、超时、取消、锁、连接／任务生命周期、部分成功与恢复。作者解释帮助理解；审核者仍追踪实际分支、状态和资源责任。
测试有效性异常／并发／重复等适用场景；是否 mock 掉目标；是否缺状态和副作用断言。预期来自需求／契约，实际执行当前代码；覆盖率和退出码仅作辅助。
静态与一致性命名、风格、复杂度、重复、日志规范、硬编码等。优先复用项目现有工具与阈值；不为统一风格扩大无关重写。
安全注入、资源归属、越权、秘密、敏感信息、上传／外部请求等相关攻击路径。允许和拒绝配对，普通用户／相关租户范围，必要脱敏与无副作用验证。
可观测性与运行风险现有日志／指标能否发现与定位故障，兼容、容量及恢复边界。补确有必要的缺口；避免敏感日志、高基数指标、无行动价值告警。
以下结果不能单独证明功能通过

只有 lint／构建通过；测试退出码为零但空套件或全跳过；仅 dry-run；只断言 mock 自己配置的值；沿用旧代码的报告；“AI 解释说没有问题”。作者自查有价值，但必须结合独立确定的预期、实际执行和适当复核。

每次验证至少记录：代码／构建对应关系、用例／需求、时间与环境、命令或操作、实际数量、业务断言、失败／跳过、真实与模拟范围、剩余缺口。修改后按影响重跑，避免无理由重复全量。

三类 HTML 文档的写作与完成标准

正式需求、技术设计和两岗位测试用例均为实际可单独打开的 HTML 文件：UTF-8、内嵌样式、目录锚点、可读表格、直接可见图示。默认不依赖 CDN、在线字体或打开后下载的图表库。计划、状态、提测索引和运行报告没有统一改为 HTML 的要求；脚本继续使用实际测试语言。

9.1 · PRD：先说明问题、目标与边界，再进入功能
PRD 固定十部分
顺序章节写到什么程度
1背景与问题谁在什么场景遇到什么问题，现状证据与影响，区分观察和假设。
2目标与指标价值、指标定义／计算口径、基线与来源、目标、观察周期、数据来源与负责方。未知数字保留待决。
3范围（含不做）包含、排除、一期／二期／未定、角色和对象边界。P0／P1／P2 与分期分开。
4用户场景与流程角色、触发、前提、主路径、结束状态和相关异常出口，流程图配解释。
5功能需求稳定编号、优先级、分期、来源、主流程、规则表／状态机／决策表、异常与字段定义、关联 AC。
6非功能与依赖性能、安全、权限、合规、可观测性、发布恢复；上下游／接口／数据依赖、可用条件与顺序。
7数据与埋点来源、归属、生命周期、隐私；事件、触发、属性、去重／统计口径和对应指标。
8验收标准每条需求有可观察的前提、动作、结果与必要副作用，稳定 AC；非功能也有验证办法。
9风险与灰度回滚风险／触发／影响／应对／负责方，真实启用机制、监测、暂停／回滚条件和数据边界。
10变更记录版本、日期、内容及原因、受影响 REQ／AC、下游更新状态和确认依据。

每个功能最低要求：主流程完整；失败、超时、并发、重复提交、权限不足、空数据、边界值逐项说明适用规则／不适用理由／待确认影响；业务规则用表格、状态机或决策表表达，禁止用“大概、尽量、友好提示”等无法判断的规范性表述。

字段表不可缺：名称、业务含义、类型、必填／条件必填、长度或范围与单位、默认值、校验、来源。没有约束或默认值就明确写出，不擅自补成 255 等常用数字。

关键选择：写真实选项、比较依据、取舍和拍板建议；只有一个满足约束的方案时说明原因。实现架构、表结构和锁策略留给技术设计，除非本就是已有约束。

研发是否无需猜关键业务规则？测试能否据此写全用例？业务方能否说明上线价值？三个月后新人能否读懂选择原因？这四问通过仍需既定需求确认，不能跳过后续设计。

一份登记区分身份、计划与实际交付

交付前后怎样维护知识

交付前持续修订当前有效产物，并按既定规则处理确认变化。交付时保存对应代码、文档修订、确认与证据的基线；后续实质变更建立关联特性包，说明继承、扩展或替代关系。勘误保留原因与基线对应关系。重要跨特性决定可以沉淀到长期决策记录，再从相关特性引用。

模块索引回答“现在从哪里了解这个模块”。按实际落地内容维护当前规则、架构、契约、已知限制及其来源，注明代码／适用版本和验证状态。已有权威正文时直接链接复用，内容只有一个有效维护位置。特性包提供本次变更的范围、决定与历史依据。

让证据顺着同一条链可查

稳定 feature_id→REQ／AC→设计／INV／契约→任务与用例→代码／脚本版本→逐次运行证据→范围结论

每次运行采用独立 run-id 追加记录，包含实际代码／构建、环境、用例与断言、结果及真实性边界。Git 中保留关键摘要和可持久访问的证据引用；大日志、视频、Trace 等沿用团队 CI／制品存储，并明确保存期限和访问前提。有工作区改动时保留相关差异摘要／指纹，无 Git 工程可使用相关文件指纹。

需求、设计、用例各维护一个有效来源；机器可读数据可从同一结构化定义生成。旧 Markdown／Word 等可作输入。内容变化按影响更新下游，完整写出 REQ／AC／用例及其来源标识，编号不因排序任意重编。

跨岗位交接使用可访问的版本依据

两岗位通过稳定特性标识、需求／契约修订和确定构建关联。QA 的用例、脚本和结果归独立验收工程，应用包可用 acceptance_reference 关联其入口。材料采用团队可访问引用或授权交付的快照，实际送达与发布状态依事实登记。

人工确认、变更与任务接续

确认节点：来源、内容、版本必须对应
节点／事件必须做的判断允许继续的工作
需求闭环四维和 PRD 完成标准满足；真实用户确认当前内容与版本。确认后设计及两岗位业务用例可推进；确认前继续事实调查与独立准备。
设计确认关键机制、契约、状态、失败与验证边界明确；真实用户确认当前方案。确认后实施准备与编码；范围内业务用例可独立准备。
重大偏差／高风险取舍有影响证据、未知、选项与推荐，明确变更哪些已确认内容。待答时继续不依赖该答案的授权工作；不自行拍板业务取舍。
普通细节在已确认规则与设计范围内，不改变核心契约、风险或范围。自主推进，不新增固定确认节点。
QA 岗位确认实际运行结果与范围有依据，由测试工程师负责结论确认。AI 据实汇报执行和限制，不能代签。

变更时只使受影响部分失效

需求变 → 查设计和用例→设计变 → 查实现与用例→代码变 → 查开发及验收证据→按影响重确认／重跑

保留仍有效的确认、文档与测试；不凭一份旧“通过”覆盖新代码，也不无理由重做整套流程。关键变更同步正文、图示、契约、状态表和引用；修改标题／编号后检查所有受影响锚点与交叉引用。

  4. 保留有效工作，列出最近一个未满足的必要条件，从那里继续；路径变化时同步登记、索引与引用。

常见情况：不要用流程捷径替代证据

简单 UI 图标／样式 Bug按五项评估做局部修复、必要源码／静态检查及可行非 UI 验证，记录显示验证缺口。不为此在研发中执行浏览器／截图／手工 UI 验收；显示正确性留给 QA。
测试聚合命令包含 UI／真实 E2E先读配置，选择符合开发期的单元／接口／非 UI 功能子集，检查 hooks／watch／CI 同样遵守。不能直接跑聚合入口而提前触发后置测试。
mock 通过，但 SQL／事务／消息语义未知保留真实目标逻辑证据，列出无法证明的真实兼容性、锁／事务或投递场景。交 QA 补真实证据；不能称真实落库／送达已验证。
源码、文档和生产现象不一致追踪调用与真实入口，明确证据类型和对应版本，必要时做范围受控调查。代码存在不证明路径正在使用，源码不等于已验证生产事实。
缺验收工程或共享环境工程未知先准备场景，写脚本前明确；环境缺失保留未验证、最小补验动作和实际协作方。不猜路径写回应用 test/，不自动要求开发者复刻线上。

发现验收预期与需求冲突回到有效规则和契约核对；规则不清回需求，契约不清回设计。不能为通过而删断言、扩大 mock 或改预期。
grilling／协作能力不可用如实说明依赖或能力限制；当前 agent 继续获准的事实调查，决策缺口保持可见。不假称已使用技能或获得独立评审，也不代替用户决定业务。
同一人承担研发与测试岗位明确切换岗位任务、工程、版本和结果；高风险工作安排适当独立复核。角色改名不产生独立性；不把开发自查视为独立验收。
变更反复扩大或同类失败反复出现重新报告根因、影响、未知、选择和推荐，与用户决定下一步。必要时重选阶段，保留仍有效工作。
验收通过后准备合并／发布按照已有授权与实际项目发布规则处理，并核对适用监测与恢复安排。验收结论不自动授权推送、合并、部署或外部通知；代码回滚不自动恢复数据。

在成本可控的前提下保住质量

  • 按需读取当前阶段与直接依赖，不一次装入全部 skill 或全仓文档。
  • 复用有效确认、用例、fixture、框架与扫描工具，修改后只重跑受影响检查，再在合适节点汇总必要回归。
  • 优先使用最低成本且足以证明目标的层级；不为 mock 强行重构，也不为检查一次页面部署整套线上环境。
  • 记录耗时和真实失败原因，优化慢步骤与隔离边界；不能靠删场景、断言或夸大结论节省 token。
  • 方案深度随风险调整：简单 Bug 用短记录，复杂行为保留必要状态、失败和副作用细节。

统一概念、名称与质量反馈

需求、设计、用例、任务与代码沿用同一业务含义。项目已有词典位置和格式优先；新概念或无法解释的冲突才使用 domain-modeling，已有定义明确的简单 Bug 直接继续工作。

内容维护位置与规则示例
业务概念相关词典；规范名、简短定义、范围、易混对象与必要关系。导出任务是一项用户工作；执行尝试是它的一次运行，不能机械合并。
技术名称映射设计或已有模块契约；关联职责、代码、接口、存储及展示名。业务叫导出任务、旧 API 叫 export_jobs，可以有明确兼容映射。
本次变化需求／设计及特性登记的来源引用；候选与确认目标分开。没有实现的新定义不写成当前生产事实，不能覆盖旧交付记录。
重要决定局部取舍留设计，跨特性重要决定按需 ADR；项目强制记录照常遵循。难逆转、有真实备选、缺背景难理解的选择值得单独留下理由。

各阶段怎么做

  • 需求阶段核对对象、关系和规范名称，新定义随需求确认；设计阶段补技术映射、职责与图示。
  • 用例使用同一对象、状态和预期；计划与实现沿用已确认名称，旧技术标识按真实兼容关系处理。
  • 审核同时核对正文、图、契约、测试与代码含义；词面扫描只是疑点，合理别名及历史引用不自动打回。
  • 交接给出术语基线、增量及待测构建；QA 不用新版词典重写旧构建预期。

用真实反馈判断质量

  • 复杂 Bug 先取得捕捉用户原症状的证据，再用可证伪假设探测、修复和复核；反馈无法取得时说明已试方法与缺口，不猜成已修。
  • 关键测试的期望来自需求、契约或独立算例，不能用与实现相同的算法重新生成，也不能把目标业务或权限 mock 成成功。
  • 审核声明起点和实际终点。范围包含工作区时，检查已提交、暂存、未暂存及相关未跟踪文件，不能只审旧 HEAD；按最终内容避免重复计数。
  • 分别呈现需求／设计符合性和项目规范符合性，保留全部适用风险维度；发现有证据，阻塞修复后定向复核。两个标题不等于两次独立审核。

控制流程与维护成本

任务优先按可验证业务行为纵向拆分，广泛迁移保留兼容顺序；资料按需加载，共用规则只维护一处。图解或逻辑原型用于真实的重要未知，不成为每次任务的附加阶段。提交说明用变化、前后证据、影响与可逆性即可，不为小改动强制绘图。

用户要求复盘或反复高代价失败时，再改善导航、规则或工具；机械失误优先交已有检查器。新增守卫应在隔离样例中观察通过、故意违规失败、恢复通过，不自动增加产品 UI／真实 E2E 或每次全量环境治理。

完成与未验证分开

文件与模板完整、安装路径正确、隔离试用通过和各 Agent 原生会话通过分别报告。保留有效证据，只对实际变化或失败重跑必要检查，不用一次试用宣称固定节省 token 或零 Bug。
